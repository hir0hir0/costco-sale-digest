# レビュー運用手順（costco-sale-digest）

## 0. 前提（確定済み・2026-08-31）

`docs/review/personas.md` の「確定した前提」を参照。要点：

- レシートは自分の購入分のみ
- **第一の利用者は自分（P0）**。一般ユーザ向けの作り込みは第2段階
- メルマガ・レシートの両方が正規のデータ。ただし**答える問いが違う**ので、混ぜるなら規則が要る
- メルマガは全国共通。店舗軸が要るのはレシート側だけ
- **サイトは公開する。ただし購入日は月単位・店舗と数量は出さない**（公開ポリシー表）

前提が変わったら、**まずこのファイルとpersonas.mdを直してからレビューを回す。**

## フェーズ

| | 今（第1段階） | 第2段階 |
|---|---|---|
| 利用者 | 自分だけ | 一般公開 |
| 標準レビュー | `/review-site`（5体） | `/review-site all`（9体） |
| 重点 | 取り込みの正しさ・データ整合性・店頭での実用 | 初見の分かりやすさ・公開リスク・競合優位 |
| ブラックボックス | まだ不要 | 必須 |

## 2つのレーン

| | 監査レーン | 提案レーン |
|---|---|---|
| 問い | 壊れているものは何か | 無いものは何か |
| コマンド | `/review-site` | `/propose` |
| 様式 | `review-format.md` | `proposal-format.md` |
| 出力 | 深刻度順の指摘 → 直すべき3件 | 提案 → 次に作る3件 |
| 絞り込み役 | review-critic | proposal-triage |
| 頻度 | 変更のたび | 月1、または手が空いたとき |

**同じ実行に混ぜない。** 混ぜると「欠陥ではないが言いたいこと」が Major に化け、
逆に良い提案が Idea として埋もれる。監査中に浮かんだ提案は1行メモに留めて `/propose` に送る。

## 1. ホワイトボックス側（コードとデータを見せる）

**セッションは `costco-sale-digest` を選んで開く**（`bsf-reserver` ではない）。

```
/review-site
```
→ 標準5体（receipt-pipeline / data-integrity / docs-drift / ops-resilience / mobile-a11y）+ 反証

```
/review-site all
```
→ 9体すべて。公開に踏み切る前や、大きな機能追加のあとに。

```
/review-site receipt-pipeline data-integrity
```
→ 観点を絞る。

## 1-b. 提案レーン

```
/propose            # 機能提案 + 見せ方提案 → 3件に絞る
/propose feature    # 機能だけ
/propose viz        # 見せ方だけ
```

提案は**実データを見てから発想させる**設計になっている。データが薄いうちに回しても
「データが溜まったらできること」しか出てこないので、**ある程度データが溜まってから**が効く。

## 2. ブラックボックス側（初見ユーザ視点）

`blackbox/` の中身を、**costco-sale-digest とは別の場所**で使う。方法は2つ。

- **A（推奨・手軽）**: 通常のClaudeチャットを新規で開き、`blackbox/tasks.md` とスクリーンショットを添付して
  `blackbox/.claude/agents/first-time-user.md` の本文をそのまま貼って指示する。
- **B**: 別リポジトリ（例 `costco-blackbox`）を作り、`blackbox/` の中身を置いてセッションを開く。

**同じセッションでホワイトボックスとブラックボックスを混ぜない。**
コードを読んだ知識が「初見ユーザには分からない」という判断を汚染する。

## 3. サイクル

| タイミング | 回すもの |
|---|---|
| レシート取り込みロジックを触ったあと | `/review-site receipt-pipeline data-integrity` |
| メルマガ取り込みを触ったあと | `/review-site ops-resilience data-integrity` |
| ふだんの定期チェック | `/review-site`（標準5体 + 反証） |
| CLAUDE.md を更新したあと／しばらく更新していないとき | `/review-site docs-drift` |
| **サイトを公開する前** | `/review-site legal-risk`（**必須**。Git履歴の個人情報まで見る） |
| 公開後の大きな機能追加のあと | `/review-site all` |
| 公開後・月1 | ブラックボックス（慣れによる盲点の再チェック） |
| 月1、または「次に何作ろう」と思ったとき | `/propose` |

## 4. 指摘の扱い方

`final.md` が出たら、**全部直そうとしない**。

1. Critical は全て対応
2. Major は「personas.md の**★付きタスク**のどれを塞いでいるか」で並べ、上位3件だけ着手（☆は後回し）
3. Minor / Idea は `docs/review/backlog.md` に積むだけ
4. final.md の「CLAUDE.md への追記提案」を確認し、採用するものだけ CLAUDE.md に反映する

レビューの価値は指摘数ではなく、**直す順番が決まること**にある。
提案レーンも同じで、価値は提案数ではなく**次に作るものが1つ決まること**にある。

## 5. このリポジトリ特有の注意

- レビュワーは `CLAUDE.md` を読む前提で書かれている。CLAUDE.md が古いとレビュー全体が誤誘導される。
  だから `docs-drift-reviewer` を入れてある。**迷ったらまずこれを回す。**
- レシート由来データを扱う都合上、`legal-risk-reviewer` は Git 履歴まで見る。
  リポジトリを public にする前には必ず単独で回すこと。
