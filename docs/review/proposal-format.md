# 提案出力様式（提案レーン共通・厳守）

**これは監査（review-format.md）とは別のレーンです。**
監査は「壊れているものを見つける」、提案は「無いものを構想する」。
同じレポートに混ぜない。混ぜると、欠陥でないものが Major に化け、良い提案が Idea に埋もれる。

各提案は以下のブロックを1つ出力する。

```
### <提案名（体言止め・15文字以内）>
- **観点**: <自分のエージェント名>
- **効く相手**: <P0 / P1 / T2 のように personas.md のIDで書く。「全ユーザ」は禁止>
- **今どうしている**: <この提案が無い状態で、その人が代わりに何をしているか。1〜2文>
- **提案**: <何をどう見せる／できるようにするか。画面の姿が浮かぶ具体度で>
- **実現区分**: <即実装可 / 要データ追加 / 要前提変更> ← 下表参照
- **必要なデータ**: <既存のどのデータで足りるか。足りないなら何を追加取得するか>
- **効果**: <大 / 中 / 小> ＋ 一行の根拠
- **実装コスト**: <小 / 中 / 大>
- **やめておく理由になりうること**: <この提案の弱点を自分で書く。必ず1つは書く>
```

## 実現区分

| 区分 | 定義 |
|---|---|
| **即実装可** | 今あるデータだけで実現できる。取り込みロジックを変えない |
| **要データ追加** | 取り込む項目を増やす／新しい情報源が要る |
| **要前提変更** | personas.md の「確定した前提」や「やらないこと」に触れる |

**「要前提変更」の提案は歓迎するが、どの前提をどう変えることになるかを明記すること。**
黙って前提を無視した提案は無効。

## 禁止事項

- **一般論の羅列。**「ダークモード対応」「SNS共有ボタン」のような、このサイト固有でない提案は出さない。
- **データの裏付けがない提案。** 実際に蓄積されているデータを見て、それで何ができるかから発想する。
  「こういうデータがあれば面白い」ではなく「**このデータがあるから、これができる**」。
- **1エージェントあたり最大8件。** 数を出すことに価値はない。
- **監査に属する指摘を混ぜない。** 「〜が壊れている」は review-format.md 側の仕事。

## 最後に必ず付けるサマリ

```
## サマリ（<エージェント名>）
- 即実装可: N件 / 要データ追加: N件 / 要前提変更: N件
- **1つだけ作るなら**: <提案名と、その理由1文>
- **このサイトが持っていて他が持てない資産**: <1文。無いと思うならそう書く>
```
